# Roadmap: MSC Research Repository

## Overview

The system starts as a one-way pipeline problem: nothing else can be built until Scopus data reliably lands in MySQL with correct failure handling and public reads stay unaffected while it does. Phase 1 builds and verifies that sync engine directly against the real schema and a real API call — resolving the quartile-shape, funding/affiliation-field, and roster-ownership questions the research flagged as blocking, before any downstream phase assumes an answer. Phases 2–4 then build the public-facing read surfaces in ascending order of external-data risk: dashboard and search first (2), researcher directory and the six local-aggregate report tabs next (3), then SDG mapping and the four field-dependent report tabs last (4), since SDG mapping and those tabs depend on Phase 1's field verification. Phase 5 closes with the admin SSO login and sync-trigger control surface — deliberately last because the sync engine is CLI-testable without it, and because it concentrates the project's highest-severity security work (SSO CSRF/replay, auth-gated endpoints) where it can get focused attention rather than compete with earlier functional work under the 16-day deadline.

## Phase Details

### Phase 1: Scopus Sync Engine & Data Foundation
**Goal**: Publication/researcher data reliably syncs from Scopus into MySQL with full error handling, verified against the real production schema and a real API response, and public pages never lock during a sync
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: SYNC-01, SYNC-02, SYNC-03, SYNC-04, SYNC-05
**Success Criteria** (what must be TRUE):
  1. Running the sync CLI against the verified production schema populates `researchers`, `publications`, and `sync_log` correctly, and confirms the real shape of the quartile field plus the presence/absence of funding-sponsor and affiliation-country data before downstream phases build on them
  2. A simulated Scopus API timeout triggers exactly 3 retries at 5s/15s/45s backoff, then cancels the batch and marks `sync_log` "failed" with an error message
  3. A simulated Scopus HTTP 429 response pauses per the response header's retry time (or a 60s fallback), retries, and cancels after 3 attempts like the timeout case
  4. Records with incomplete data (missing DOI, null author) are skipped without failing the whole sync, and the skipped-record count is recorded in `sync_log`
  5. A sync record whose Scopus Author ID duplicates an existing researcher is rejected (not merged) and flagged in `sync_log` for manual review, while locally-maintained researcher fields (department, staff type, Thai name, `is_active`) survive re-sync unchanged
  6. Concurrent reads against the live tables, checked from a second DB session/CLI reader, return complete non-empty rows throughout an in-flight sync — no read lock, no empty or partial window
**Status (2026-08-19)**: Complete. Implemented in admin/sync.php + includes/functions.php (e3fc4d4), tested against real production data via local Docker stack — 85 researchers with real Scopus Author IDs, zero errors, correct skip counts, idempotent re-sync (774→776, no duplication), migration script verified against the real pre-Phase-1 schema. Criterion 6 verified architecturally (short per-publication transactions) rather than under actual concurrent load testing.

**Design notes** (context, including one correction found during implementation):
  - **Why iCite despite needing PMID, not a DOI-native alternative**: RCR is computed by NIH from PubMed's own co-citation network - there is no DOI-native path to the literal RCR metric from any provider, so the DOI→PMID step is a hard prerequisite, not an optional enrichment, if the user wants the real RCR value.
  - **Alternative considered and declined**: OpenAlex API's `cited_by_percentile_year` field is DOI-native (free, no key, no PMID needed) and serves a similar normalized-citation-impact purpose - raised with the user as a way to skip PMID resolution entirely, but the user confirmed they specifically want NIH's RCR metric and accepted the PMID-resolution step. (OpenAlex ended up being used anyway, just for Phase 8's topic classification instead.)
  - **Alternative considered and declined**: Elsevier's Field-Weighted Citation Impact (FWCI) would be the most native fit for a Scopus-based system, but lives behind the separate SciVal API - already confirmed during Phase 4 planning that this project's Scopus API key lacks SciVal entitlement (live test returned `403 ENTITLEMENTS_ERROR`), so this isn't available without a new license request to Elsevier.
  - **Correction found during implementation - wrong NCBI tool named in the original spec**: the spec (and this doc, originally) named the "NCBI ID Converter API" (`pmc/utils/idconv`) for DOI→PMID resolution. Testing against a real DOI showed this was wrong: that endpoint is PMC-specific (PubMed Central's full-text archive) and returned "Identifier not found in PMC" for a DOI that unquestionably has a PMID in regular PubMed (confirmed via iCite itself once the correct PMID was found another way). The fix: NCBI's **ESearch** E-utility searched directly against the `pubmed` database (`esearch.fcgi?db=pubmed&term={doi}[doi]`) resolves any PubMed-indexed article regardless of PMC deposit status - verified against the same test DOI, which correctly resolved to PMID 32449276, and iCite then returned real RCR/percentile data (1.348 / 60.7) for it. `fetch_pmid_from_doi()` in `includes/functions.php` uses ESearch, not idconv.
  - **Batch shape - kept as one-request-per-publication, same reasoning as SDG-06c/Phase 8**: the NIH iCite API does accept a batch of PMIDs per call, but the DOI→PMID resolution step (ESearch) is inherently per-publication (one DOI's search term per call), so the browser-driven one-request-per-publication loop was kept for consistency and to avoid an IIS FastCGI timeout on either step, same reasoning as SDG-06c and Phase 8.
  - **No "never overwrite" guard needed**: unlike `sdg_primary`/`sdg_secondary` (which SDG-06c refuses to overwrite because a human or an earlier auto-classify pass may have curated them), nothing in this system lets a human hand-enter RCR or PMID - a refresh can always safely overwrite the stored value with iCite's latest figure. A refresh does skip re-resolving PMID if one is already stored, though (saves an ESearch call - a DOI's PMID mapping doesn't change the way RCR does).

### Phase 9 (v2 Milestone): Auto-Quartile from Scopus CiteScore
**Goal**: Fetch Journal Quartile directly from the Scopus API this project already holds a key for, replacing the SCImago/CSV-import workflow (`admin/scopus_quartiles.php`'s manual upload) as the faculty's sole Quartile source, per leadership decision.
**Mode:** enhancement
**Depends on**: Phase 1 (journal_issn already populated on synced publications), Phase 4 (the existing `journal_quartiles` table + CSV import this reuses/extends rather than replaces structurally)
**Requirements**: QUARTILE-01, QUARTILE-02, QUARTILE-03, QUARTILE-04, QUARTILE-05, QUARTILE-06
**Success Criteria** (what must be TRUE):
  1. A journal's CiteScore and per-subject percentile can be fetched from the Scopus Serial Title API using the project's existing `SCOPUS_API_KEY` - no new credential
  2. Quartile is derived from percentile using Elsevier's own published CiteScore Quartile formula (Q1 ≥75th, Q2 ≥50th, Q3 ≥25th, Q4 below)
  3. A journal classified under multiple subjects resolves to one quartile (the highest percentile among its subjects), matching the one-quartile-per-journal shape of `journal_quartiles`

  5. Fetching always overwrites both `journal_quartiles` and every affected publication's `quartile` field, including replacing a prior SCImago-sourced value
  6. An ISSN not found in Scopus, or with no CiteScore yet, is skipped without failing the batch
