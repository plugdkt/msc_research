# Stack Research

**Domain:** PHP + MySQL server-rendered research-publication dashboard/reporting system, syncing from an external REST API (Scopus), deployed on IIS (Windows Server) via self-hosted GitHub Actions runner
**Researched:** 2026-08-18
**Confidence:** MEDIUM (web-search cross-checked across multiple independent sources, plus direct WebFetch verification of php.net, Packagist, and getbootstrap.com for current version numbers; Scopus-specific API details are LOW confidence — see Gaps)

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| PHP | 8.4.x (verify against what's already installed) | Language runtime | Verified directly against php.net/supported-versions.php (2026-08-18): **8.5 is actually the newest branch** (released 20 Nov 2025, security support until 31 Dec 2029) — longer runway than 8.4 (security until 31 Dec 2028). Despite that, this stack recommends **8.4, not 8.5**, for a deliberate reason: 8.5 is ~9 months old at the time of this project, and Windows/IIS PHP builds (windows.php.net) and PECL extension DLLs for a brand-new major typically lag Linux maturity by a wider margin than on Linux — a real risk on a 16-day timeline with zero slack to debug an extension/build issue on a live faculty server. 8.4 has ~1.5 years of field use by Aug 2026 and is very likely closer to whatever the server's PHP admin tooling (e.g. PHP Manager for IIS) already lists as current. **Do not skip verifying the actual installed version** via `phpinfo()` on the live server — if it's pinned at 8.1/8.2 (8.2 security support ends 31 Dec 2026, uncomfortably close), write 8.1+-compatible syntax and treat any version bump as an infra fast-follow, not a blocker. Confidence: MEDIUM-HIGH (version data itself is HIGH — pulled directly from php.net — but the 8.4-over-8.5 call is a judgment call, not a documented fact). |
| No PHP framework (plain PHP, script-per-page + shared bootstrap) | — | Application structure | The existing legacy site already uses a flat, literal URL-per-file convention (`index.php`, `publications_search.php`, `researchers_list.php`, `reports.php`, `admin/index.php` — confirmed in SPEC.md §8). Adopting a router-based micro-framework (e.g. Slim) would require IIS URL Rewrite rules to preserve these exact paths, adding IIS-config risk and setup time neither budgeted nor necessary for a 16-day, ~5-page site. Keep the file-per-page convention, but factor shared logic (DB connection, auth guard, HTML escaping helpers, Scopus client, SDG mapping) into a `src/` class library autoloaded via Composer (PSR-4), so each page script stays a thin controller. Confidence: MEDIUM-HIGH (structural reasoning from the spec's own fixed URL contract). |
| MySQL | 8.0.x (match whatever the existing server already runs) | Database | Already locked in by the existing system (SPEC.md §5). Use `utf8mb4` charset/collation on all tables (handles Thai text — researcher names are stored in Thai and English per the data model) and the InnoDB storage engine. InnoDB matters specifically for the Availability constraint (§4.2): InnoDB's MVCC means readers see a consistent snapshot and never block behind an in-progress writer transaction — this is *why* public dashboard/search/report SELECTs stay available while a sync transaction is open, not merely "row-level locking" in the abstract. Because §6.1 requires the sync to be all-or-nothing (no partial writes on failure), wrap the whole batch — or each publication's insert/update — in an explicit transaction; MVCC means this does not block public reads either way, but a very long single transaction does hold undo-log space, so prefer committing per-publication (or per reasonably small batch) over one transaction for the entire sync run. |
| PDO (`ext-pdo_mysql`) with prepared statements, no ORM | PHP built-in | Database access layer | For ~7 tables and a read-heavy, low-write workload (~800–10,000 publications, sync-triggered writes only), a full ORM (Eloquent standalone, Doctrine) adds mapping/hydration overhead and a learning curve that doesn't pay off at this scale — research indicates ORM overhead becomes noticeable well before 10k rows, especially with the multi-table joins this project's reports need (publications ⋈ publication_authors ⋈ researchers ⋈ publication_sdgs). Prepared statements via PDO are the non-negotiable baseline for SQL-injection prevention (explicitly required in SPEC.md §9). Wrap PDO in a small `Database` class with: `PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION`, `PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC`, and **`PDO::ATTR_EMULATE_PREPARES => false`** — this last one is easy to forget and is what makes prepared statements actually native (server-side) MySQL prepares rather than PHP-side string interpolation with emulated placeholders, which matters for both correctness (type handling) and for the SQL-injection guarantee the spec requires. Confidence: MEDIUM. |

### Supporting Libraries

| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| `guzzlehttp/guzzle` | **^7.9** (not 8.0) | HTTP client for calling the Scopus REST API and the MEDSCI ACC `verify.php` SSO endpoint | Verified via Packagist: the actual latest release is **Guzzle 8.0.2, published 2026-08-05** — only ~2 weeks old at the time of this research. ## Installation

```bash
# Core dependency management (run on the self-hosted runner during CI, not on IIS directly)
composer require guzzlehttp/guzzle:^7.9 vlucas/phpdotenv:^5.6 monolog/monolog:^3.0

# Frontend: no npm/build step needed — vendor Bootstrap 5.3.8 + Chart.js 4.x as static
# files checked into a /public/vendor/ directory, or reference via CDN with a
# Subresource Integrity (SRI) hash if the deployed server has outbound internet access.
# This avoids needing Node.js on the Windows self-hosted runner at all.

# Dev-only (not deployed)
composer require --dev phpunit/phpunit:^11.0
```

Slim is a legitimate, well-supported choice (12k+ GitHub stars, zero-dependency core, PSR-7/PSR-15 middleware) for a project this size — rejected here specifically because it fights the existing fixed-URL convention and IIS rewrite setup isn't budgeted in a 16-day timeline, not because it's a bad framework. |
| PDO + prepared statements, no ORM | Doctrine DBAL / a query builder like Medoo | Use a query builder if the reports page's multi-dimension aggregation queries (§4.1: trends, department breakdown, quartiles, SDGs, rankings, sources, author roles — up to ~10 report "tabs") become unwieldy to hand-write and re-use as raw SQL strings. Do not reach for a full ORM (Eloquent standalone/Doctrine ORM) at this data scale. |
| Bootstrap 5.3.8 | Tailwind CSS | Use Tailwind only if a future milestone needs a fully custom, on-brand design system with a dedicated frontend developer and time budget for a build pipeline (PostCSS/CLI, requiring Node.js on the deploy runner). For a 16-day build of ~5 page types heavy on tables, filters, pagination, tabs, and badges — Bootstrap's strong suit — Tailwind's setup cost outweighs its benefits here. State of CSS 2025 shows Tailwind ahead on usage (37% vs 21.6%) and satisfaction, but that lead assumes a build pipeline is already worth having; Bootstrap is repeatedly named the faster choice for rapid MVP builds in 2025/2026 comparisons. |
| Guzzle 7.x for HTTP calls | Raw PHP `curl_*()` functions | Only use raw cURL for zero third-party dependencies. | Guzzle ^7.9 | Guzzle 8.0.2 (current latest on Packagist, released 2026-08-05) | Adopt 8.x once it has a few months of production use across the ecosystem — not for a project with this deadline and no regression budget. |
| Windows Task Scheduler (or detached process spawn) for the sync job | A "fake cron" approach (sync triggered on public page load) | Never use page-load-triggered sync — the spec explicitly requires public pages to stay available and unaffected during sync, and request-triggered sync ties the job's lifetime to a single HTTP request/IIS worker thread, fragile for a multi-minute, API-bound, retrying job. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| Laravel / Symfony (full-stack frameworks) | Overkill for a ~5-page read-only site + one admin action; both assume conventions (routing, service container, ORM-first data access, templating, rewrite-based URL handling) that fight the existing fixed-URL IIS deployment, consuming timeline on setup rather than features. | Plain PHP + Composer-autoloaded shared library. |
| Eloquent (standalone) or any ORM for this data model | ORM overhead becomes noticeable well before 10k rows, especially with joins — and this project's core value (multi-dimension reports) is exactly joins-and-aggregation-heavy. | PDO + prepared statements, optionally a thin query builder if raw SQL repetition becomes painful. |
| `CURLOPT_SSL_VERIFYPEER => false` anywhere in the codebase | SPEC.md §9 explicitly flags that the vendor's own SSO sample code disables this and forbids copying it as-is. | `CURLOPT_SSL_VERIFYPEER => true` (raw cURL) or Guzzle's default `verify => true` — verify this is never overridden. |
| Tailwind CSS with a Node.js build step on the Windows self-hosted runner | Adds a second toolchain (Node + PostCSS/CLI) to a Windows Server the team doesn't otherwise need Node on, purely for standard dashboard/table/form UI. Extra CI moving part = extra failure mode in a 16-day timeline. | Bootstrap 5.3.8 via CDN or vendored static files — zero build step. |
| Relying on IIS/FastCGI request timeout to run the Scopus sync inline in the admin POST handler | IIS's default FastCGI timeout (commonly 90s–120s) will likely kill a multi-page Scopus paginated fetch + retry-with-backoff job (worst case: 3 retries × up to 45s, before any data processing) mid-request, leaving sync inconsistent and violating the "reject overlapping sync, don't half-write" requirement. | Detached PHP CLI process or Windows Task Scheduler task, running independently of the IIS worker process lifecycle (see pattern below). |
| Assuming Scopus rate-limit responses carry a `Retry-After` header | Not confirmed for Scopus/Elsevier's Research Products APIs — see Scopus-Specific Notes below; documented headers are `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (epoch seconds), not `Retry-After`. | Key the 429 backoff decider off `X-RateLimit-Reset` when present, falling back to the spec's flat 60s wait when it's absent (§6.1 already specifies this fallback). |
| Committing `vendor/` or a generated `.env`/`config.php` with real secrets to git | Explicitly forbidden by SPEC.md §9/§10.1. | `.gitignore` these; have the GitHub Actions workflow generate the config file on the runner from GitHub Secrets at deploy time, writing it outside the IIS webroot. |

## Stack Patterns by Variant

**Background Sync Job Pattern (no persistent worker, IIS/FastCGI environment):**

1. **Preferred (most robust): pre-registered Windows Scheduled Task, triggered on-demand.** Register one Scheduled Task (`schtasks /create ...`, one-time server setup, not part of app deployment) that runs `php.exe C:\path\to\sync.php` with no execution time limit, under a service account with DB + outbound HTTPS access. The admin panel's "sync now" button (a) checks/sets the `sync_log` lock row, then (b) shells out to `schtasks /run /tn "MSCResearchSync"` via `exec()`, which returns almost instantly — the actual Scopus fetch/retry/DB-write work happens in a separate OS process, decoupled from the IIS worker and immune to FastCGI timeouts or app-pool recycles. **Known failure mode to plan for up front:** the IIS app-pool identity (typically `IIS AppPool\<name>` or `NETWORK SERVICE`) that runs the PHP web request usually does **not** have permission to trigger a Scheduled Task registered under a different account — `schtasks /run` will fail silently or with an access-denied error if this isn't configured (grant the app-pool identity "Run a task" rights via `schtasks /change` or Task Scheduler's task-level security, or register the task to run as the same identity). Verify this in the first days of implementation, not at the end — it's the single most likely silent failure in this whole pattern. This also requires IT approval to register a Scheduled Task, which SPEC.md §12 already flags as an open question — resolve it early since it determines which of these two patterns to build.
2. **Fallback (if IT will not allow a registered Scheduled Task): detached process spawn directly from the admin trigger.** From the admin POST handler, use `proc_open()` with a Windows detached-launch invocation (`cmd /c start /B php.exe sync.php`, redirecting stdout/stderr to a log file, closing pipes so PHP doesn't block on the child) to fire the sync as an independent process before the HTTP response returns "sync started." Requires `exec`/`proc_open` to not be in `php.ini`'s `disable_functions` — confirm on the actual server. Less robust than option 1 (won't survive an IIS app-pool *recycle* the same way a fully OS-scheduled task does), but needs no extra IT sign-off beyond existing admin access to the server.
3. **Do not** run the sync inline in the HTTP request, and do not reach for a PHP job-queue library with a long-running consumer — that reintroduces the "persistent worker process" this environment doesn't support.

**If the actual PHP version on the production IIS server is older than expected (e.g. still 7.4/8.0/8.1):**
- Do not silently write 8.4-only syntax. Check `phpinfo()` on the live server before writing code — SPEC.md §11 already earmarks 18–19 Aug for verifying the existing DB schema; extend that same window to confirm the PHP version. If the server can't be upgraded within the 16-day window, target 8.1-compatible syntax (still supports enums, readonly properties, named arguments) and treat the version bump as a fast-follow.

## Scopus-Specific API Notes (LOW confidence — verify against actual dev.elsevier.com docs before implementation)

- **Auth scheme:** Elsevier APIs use an `X-ELS-APIKey` header for the API key; remote (off-campus/off-VPN) access may additionally require an `insttoken` (Elsevier-issued institutional token) — confirm whether the faculty's existing Scopus access requires this for server-to-server calls from the IIS box.
- **Rate limiting:** Elsevier's documented pattern uses `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (epoch seconds) response headers, with quotas reset on a rolling window (commonly cited as 7 days) and **varying per API** (e.g. ~5,000 retrieval requests vs. ~20,000 search requests per key, per some third-party documentation — verify actual current values on dev.elsevier.com, do not hard-code these numbers). A `Retry-After` header was **not confirmed** in available sources — build the 429 decider to check `X-RateLimit-Reset` first, and fall back to the spec's flat 60-second wait (§6.1) when no usable reset time is present, rather than assuming `Retry-After` will be there.
- **SDG mapping source — highest-risk unknown in the entire stack.** Research strongly suggests SDG classification/relevance scoring in the Elsevier ecosystem is computed via **SciVal** (built on top of Scopus data, using the Elsevier Fingerprint Engine), not returned as a plain field on the standard Scopus Search API response. If that's accurate for this project, it has real stack consequences, not just a data-mapping detail: it may mean a **second API client with separate auth/entitlement** (SciVal has its own API key and license, distinct from a Scopus Search API subscription), and the faculty may or may not currently hold a SciVal license at all. This directly matches the open question already flagged in SPEC.md §12 ("Scopus API field ที่ให้ค่า SDG weight") and in PROJECT.md — treat resolving it as a **prerequisite to finalizing the SDG mapping phase's architecture**, not a detail to sort out during implementation. If SciVal access isn't available, the fallback options (compute an approximate SDG classification independently, or drop automatic SDG weighting to a manual/deferred feature) are a product decision that needs to happen before that phase is planned, not during it.

## Gaps to Address / Confidence Notes

- **PHP, Guzzle, and Bootstrap version numbers in this document are HIGH confidence** — verified directly via WebFetch against php.net/supported-versions.php, packagist.org/packages/guzzlehttp/guzzle, and getbootstrap.com/docs/versions/ on 2026-08-18, not from stale training data. The judgment calls layered on top of those facts (8.4-over-8.5, 7.x-over-8.0-Guzzle) are explicitly reasoned above — revisit both if the project timeline changes or if IT already has a specific PHP version mandated.
- **The Windows Task Scheduler vs. detached-process sync pattern is a design recommendation synthesized from general Windows/PHP sync-job practices, not IIS-official or Scopus-specific documentation.** This is the single most important "flag for deeper phase-specific research" item in the whole stack — it determines the sync feature's reliability and depends on an IT policy answer (registering a Scheduled Task) already flagged as unresolved in SPEC.md §12. Do not finalize the sync job architecture until that's answered, and budget time to verify the app-pool-identity permission issue noted above.
- **Scopus API auth header, rate-limit header scheme, and (most importantly) the SDG-weight data source are LOW confidence**, based on third-party/community documentation rather than dev.elsevier.com itself (not directly fetchable without an Elsevier developer account in this research pass). Treat the SDG-source question in particular as a blocking prerequisite for planning that phase — see the dedicated note above.
- **ORM-vs-PDO recommendation is LOW-confidence sourcing** (one aggregated web-search summary, not independently double-verified) but the *conclusion* aligns with this project's own scale (SPEC.md §4.2 target of 10,000 publications / 500 researchers), which multiple sources describe as well within "too small to benefit from an ORM" territory — treat the conclusion as solid even though the citation trail is thin.
